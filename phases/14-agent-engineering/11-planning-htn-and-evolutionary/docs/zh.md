# 用 HTN 与进化搜索做规划

> 符号规划处理「计划可被证明正确」的情形。进化代码搜索处理「适应度函数可被机器校验」的情形。ChatHTN（2025）和 AlphaEvolve（2025）展示了各自与 LLM 搭配时能解锁什么。

**Type:** Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 02 (ReWOO and Plan-and-Execute)
**Time:** ~75 minutes

## 学习目标

- 解释分层任务网络（HTN）：任务、方法、算子、前提条件、效果。
- 描述 ChatHTN 的混合循环——带 LLM 回退分解的符号搜索。
- 解释 AlphaEvolve 的进化循环，以及为什么它只能配合程序化评估器工作。
- 用标准库实现一个玩具 HTN 规划器加一个玩具进化搜索。

## 问题

ReWOO（第 02 课）、Plan-and-Execute 和 ReAct 覆盖了大多数智能体规划。有两种情形它们覆盖得不好：

1. **可被证明正确的计划。** 调度、航线规划、合规工作流——计划必须按构造就是可靠的。一份流利但偶尔幻觉出一步的 LLM 计划是不可接受的。
2. **带机器可校验适应度函数的优化。** 矩阵乘法、调度启发式、编译器 pass——目标不是「一份正确的计划」，而是「最好的计划」。

HTN 规划和 AlphaEvolve 各自解决这两种不同的问题。两者都把 LLM 当作放大器，而不是替代品。

## 概念

### 分层任务网络

一个 HTN 由以下构成：

- **任务（Tasks）** —— 复合任务（待分解）和原语任务（可直接执行）。
- **方法（Methods）** —— 把复合任务分解成子任务的方式，带前提条件。
- **算子（Operators）** —— 带前提条件和效果的原语动作。
- **状态（State）** —— 一组事实。

规划：给定一个目标任务和一个初始状态，找到一个分解，把它展开成一组前提条件按顺序被满足的原语算子。

HTN 比 LLM 更古老，至今仍是可证明正确计划的参考。

### ChatHTN（Gopalakrishnan 等人，2025）

ChatHTN（arXiv:2505.11814）把符号 HTN 与 LLM 查询交织在一起：

1. 尝试用已有方法分解当前复合任务。
2. 如果没有方法适用，就问 LLM：「你会如何分解状态 `s` 下的任务 `task`？」
3. 把 LLM 的回复翻译成候选子任务。
4. 对照算子 schema 校验；拒绝无效的分解。
5. 递归。

论文的核心主张：产出的每一份计划都是可证明可靠的，因为 LLM 建议只以候选分解的形式进入，永远不会作为直接的计划编辑。符号层拥有正确性；LLM 扩展方法库。

在线方法学习（OpenReview `gwYEDY9j2x`，2025 年的后续工作）加入了一个 learner，通过回归把 LLM 产出的分解泛化——把 LLM 查询频率最多降低 75%。

### AlphaEvolve（Novikov 等人，2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）是另一类东西：由 Gemini 2.0 Flash/Pro 组合编排的进化代码搜索。

循环：

1. 从一个种子程序 + 一个程序化评估器（返回一个适应度分数）开始。
2. LLM 组合提出变异。
3. 让变异跑过评估器。
4. 保留最好的；再次变异。

已发表的战果：

- 56 年来首次改进 Strassen 的 4x4 复矩阵乘法（48 次标量乘法）。
- 用一个 Borg 调度启发式恢复了 0.7% 的 Google 算力。
- 在一个前沿工作负载上取得 32% 的 FlashAttention 加速。

硬约束：适应度函数必须可被机器校验。对散文式答案做进化搜索不会收敛。

### 什么时候用哪个

| 问题类别 | 使用 | 为什么 |
|---------------|-----|-----|
| 带硬约束的调度 | HTN + ChatHTN | 可证明的可靠性 |
| 编译器优化 | AlphaEvolve | 机器可校验的适应度 |
| 多步任务执行 | ReAct / ReWOO | LLM 在环中，无形式保证 |
| 带测试的代码改进 | AlphaEvolve | 测试就是评估器 |
| 受策略约束的自动化 | HTN | 前提条件编码了策略 |

### 这个模式在哪里会出问题

- **没有算子的 HTN。** 没有前提/效果 schema，可靠性主张就崩塌了。ChatHTN 的「LLM 建议分解」要求 schema 去拒绝无效的动作。
- **没有真评估器的 AlphaEvolve。** 「问 LLM 代码是不是变好了」不是一个适应度函数。评估器必须是确定性的、快速的。
- **过度工程。** 大多数智能体任务两者都不需要。先考虑 ReAct 或 ReWOO。

## Build It

`code/main.py` 实现了两个玩具：

- 一个标准库 HTN 规划器，带算子、方法、前提条件、效果，以及一个 `LLMFallback`，当没有方法匹配某个复合任务时介入。「LLM」是一个脚本化的分解器，这样规划器可以离线运行。
- 一个标准库的算术程序进化搜索：在测试集上生长那些让输出最小化 `|f(x) - target|` 的表达式。评估器是确定性的。

运行它：

```
python3 code/main.py
```

trace 展示了 HTN 规划器分解一个复合任务（中途有一次 LLM 回退），以及进化循环收敛到目标表达式。

## Use It

- **HTN 规划器** —— `pyhop`、`SHOP3`，或为领域专用策略执行自建一个。
- **ChatHTN** —— 研究代码；这个模式（符号 + LLM 回退）可以干净地移植到任意 HTN 规划器。
- **AlphaEvolve** —— DeepMind 论文；这个模式（组合 + 评估器）是可复现的。OpenEvolve 以及类似的开源分支正在涌现。
- **智能体框架** —— 目前还没有哪个把 HTN 或 AlphaEvolve 作为一等公民。把它建成一个 subagent 或后台 worker。

## Ship It

`outputs/skill-hybrid-planner.md` 生成一个混合规划器脚手架（HTN 或进化），并把 LLM 的角色显式限定清楚。

## 练习

1. 给 HTN 规划器加回溯：当一个算子的后置条件在运行时失败时，回滚并尝试下一个方法。
2. 给 ChatHTN 加一个 LLM 方法缓存：当 LLM 在状态模式 `P` 下分解任务 `T` 时，存储结果。下次调用时先重新查方法库。
3. 把进化搜索的评估器换成一个真实测试套件。进化出一个通过 20 个测试用例的排序函数；报告收敛所需的代数。
4. 读 AlphaEvolve 的评估器设计笔记。为你关心的一个领域设计一个评估器（SQL 查询优化、测试套件最小化、部署 YAML）。
5. 组合：用 HTN 把一个复合任务分解成子任务，再对每个子任务的原语算子用进化搜索。它在哪里出彩，在哪里过度工程？

## 关键术语

| 术语 | 人们怎么说 | 它实际是什么意思 |
|------|----------------|------------------------|
| HTN | 「分层规划器」 | 带算子、前提条件、效果的任务分解 |
| Method | 「分解规则」 | 把复合任务拆成子任务的方式 |
| Operator | 「原语动作」 | 带前提条件和效果的具体步骤 |
| ChatHTN | 「LLM + HTN」 | 没有方法匹配时符号规划器询问 LLM |
| AlphaEvolve | 「进化代码搜索」 | 组合的 LLM 变异代码；确定性评估器做选择 |
| Fitness function | 「评估器」 | 对输出做确定性、机器可校验的评分 |
| Online method learning | 「缓存的 LLM 分解」 | 存储 + 泛化 LLM 计划以降低查询成本 |
