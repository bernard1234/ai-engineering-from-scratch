给定一次拟议的 agent 部署，对照十二层参考审计其成本治理器栈，并标出哪些层缺失、调得过松或调得过紧。

产出：

1. **层清单。** 对十二个参考层的每一层（按请求上限、按任务 token 预算、按任务美元预算、按工具上限、迭代上限、按分钟/小时/天/月滚动上限、速率限制、分层路由、prompt caching、context windowing、HITL checkpoint、kill switch），说明它是否已配置，以及配置值是多少。
2. **失败模式映射。** 对每种时间尺度上的失败（失控循环、缓慢泄漏、糟糕发布、合法激增），点名捕获它的具体层以及捕获多快。
3. **按工具的上限。** 列出 agent 能调用的每一个工具。对每一个，给出一个按会话的上限及理由。任何没有显式上限的工具都是一个敞开的循环。
4. **告警阈值。** 与上限分开：达到什么消费速率时会通知人工？所观察到的电商案例（$1,200 → $4,800）是周环比增长的问题，而不是月度上限的问题。
5. **Kill switch 路径。** 当某个上限触发时会发生什么？干净中止、rollback、告警、重新启用流程。确认 kill switch 在 agent 外部（agent 无法修改自己的上限）。

硬性拒绝：
- 任何没有按任务美元预算的自主部署。
- 任何没有速率限制的无人值守长程运行。
- 在新增（<30 天）工具上，工具面没有按工具的上限。
- agent 自身可以修改的 kill switch。
- 以月度上限作为唯一上限（其他所有时间尺度都无人看守）。

拒绝规则：
- 如果用户无法按当前的模型价格给最坏情况下的运行定价，拒绝，并要求给出带成本的估算。
- 如果拟议预算超过组织在单次错误上可接受的损失，拒绝，并要求更低的上限。
- 如果用户把 Auto Mode 分类器（第 10 课）当作预算的替代品，拒绝。分类器与成本是正交的；两层都必需。

输出格式：

返回一份成本治理器审计，包含：
- **层表格**（层名、是否已配置、值）
- **失败模式覆盖**（4 行：循环 / 泄漏 / 发布 / 激增）
- **按工具的上限**（工具、上限、理由）
- **告警阈值**（速率、负责人、渠道）
- **Kill switch 路径**（触发条件、动作、重新启用流程）
- **就绪度**（生产 / 预发 / 仅研究）
