给定一个拟议的进化编码循环（生成器 LLM、程序数据库、evaluator），审计其中的 evaluator。evaluator 才是架构，生成器是可以替换的。本 skill 判断这个循环有没有可能产出真正的收益，还是只会产出被 reward hacking 的垃圾。

产出：

1. **evaluator 拆解。** 说出 evaluator 报告的每一个信号：正确性、性能、资源、其他。对每个信号说明 (a) 如何度量，(b) 被钻空子有多便宜，(c) 留出输入规则是什么样。
2. **虚构面。** 列出该领域中 LLM 最可能做出的三种虚构：声称的复杂度类别、声称在边界情况下的正确性、未经测量的性能声称。说明哪一种 evaluator 信号能抓住每一种。
3. **reward hacking 面。** 列出循环可能在不完成预期任务的情况下最大化分数的三种方式（通过测试的捷径、代理指标钻空子、背记输入）。说明各自的缓解措施。
4. **确定性与可复现性。** 要求 evaluator 输出在容差内是确定的。任何逐次运行分数波动超过种群方差的 evaluator 都要标红。
5. **部署检查。** 如果获胜变体将被交付到生产，要求一次 evaluator 不负责检查的独立部署前审查（安全、成本、人工审查）。搜索并未验证部署就绪性。

硬性拒绝：
- 任何以 LLM 评审作为 evaluator、却没有机器可校验真实基准的循环。LLM 评审可以被钻空子。
- 任何只报告单一标量分数、没有拆解的 evaluator。标量分数会放大 reward hacking。
- 只用训练集的 evaluator。留出输入不可谈判。

拒绝规则：
- 如果用户无法用两段话描述 evaluator，拒绝，并要求先给出 evaluator 规格。没有规格化 evaluator 的循环还没准备好使用算力。
- 如果领域无法验证（创意写作、开放式科学假设、长篇研究），拒绝，并建议改用人机协同的混合流水线，而不是闭环。
- 如果拟议的部署面不可逆（生产基础设施变更、在售产品中更换算法），拒绝闭环部署。要求分阶段上线和人工签核。

输出格式：

返回一页备忘录，包含：
- **循环摘要**（生成器、evaluator、目标领域）
- **evaluator 评分**（严谨度 1–5 并给出理由）
- **虚构面**（前三项，附 evaluator 覆盖情况）
- **reward hacking 面**（前三项，附缓解措施）
- **确定性与可复现性**（分数方差对比种群方差；随机种子控制；通过 / 不通过）
- **部署就绪性**（是否允许闭环交付；必需的部署前审查：安全、成本、人工）
- **建议**（继续 / 收紧 evaluator / 换一个领域）
