# Context Engineering

构建 LLM 应用时，套用这套框架来设计 context 组装流水线。

## 核心原则

1. **Context 是稀缺的。** 128K 的窗口听起来很大，但填满得很快。为每个组件显式分配预算。
2. **注意力分布不均。** 模型对开头和结尾关注更多。把关键信息放在那里。中间是死区。
3. **动态优于静态。** 不同 query 需要不同的 context。按 query 组装，而不是启动时组装一次。
4. **少即是多。** 精心编排的 10K context 胜过一股脑塞进去的 100K context。信噪比比信息总量更重要。
5. **一切都要度量。** 度量不了的东西就优化不了。每个请求都统计各组件的 token 数。

## Context 预算指引

| 组件 | 典型范围 | 优先级 | 压缩策略 |
|-----------|-------------|----------|---------------------|
| System prompt | 200-1,000 token | 固定，高 | 写紧凑，去掉冗余 |
| Tool 定义 | 500-3,000 token | 动态，中 | 按 query 意图裁剪 |
| 召回 context | 1,000-5,000 token | 动态，高 | rerank + 阈值 + 去重 |
| 对话历史 | 500-5,000 token | 动态，中 | 摘要旧轮次 |
| Few-shot 示例 | 500-2,000 token | 动态，高 | 按任务相似度挑选 |
| 用户 query | 50-500 token | 固定，最高 | N/A |
| 生成预留 | 2,000-8,000 token | 固定 | 按预期输出长度调整 |

## 各记忆类型的适用场景

**短期（对话历史）：** 当前会话。通过摘要管理。压缩超过 5-10 轮之前的轮次。最近 3-4 轮逐字保留。

**长期（事实数据库）：** 跨会话持久的偏好与项目事实。会话开始时召回。示例："用户偏好 Python"、"项目使用 PostgreSQL"、"团队采用 trunk-based development"。存储在 CLAUDE.md、数据库或结构化记忆系统中。

**情景（过往交互）：** 与当前任务相关的具体历史对话。以 embedding 形式存储，按相似度召回。"上周我们调试过一个类似的 auth 问题"就是情景记忆。

## Tool 选择策略

不要在每个请求里都包含全部 tool。这会浪费 token 并让模型困惑。

1. 对 query 意图分类（代码、邮件、日历、研究、数据）
2. 把意图映射到 tool 类别
3. 只包含匹配的 tool
4. 如果意图含糊，包含前 2 个类别中的 tool
5. 始终包含一个"通用"tool（比如 web search）作为兜底

预期节省：在意图明确的 query 上，可省下 60-80% 的 tool 定义 token。

## 召回最佳实践

- **召回后再 rerank。** 向量相似度只是粗筛。reranker（cross-encoder 或基于 LLM 的）能显著提升精确率。
- **设置相关性阈值。** 不要包含 cosine similarity 低于 0.3 的块。它们只会增加噪声。
- **去重。** 如果两个块内容重合 80% 以上，只保留分数更高的那个。
- **应用 lost-in-the-middle 排序。** 把最相关的块放在开头和结尾。
- **限制召回 token 总量。** 3-5 个高度相关的块胜过 15 个平庸的块。

## 历史管理

- 最近 3-4 轮逐字保留（模型需要近期上下文）
- 把更早的轮次摘要成文摘（"我们讨论了 X，决定了 Y，卡在 Z 上"）
- 丢弃不提供信息的系统生成轮次（没有面向用户内容的 tool 调用）
- 历史超过可用预算的 30% 时触发压缩

## 危险信号

- System prompt 超过 2,000 token：很可能包含了本应动态处理的信息
- 每个请求都带上全部 tool：去实现基于意图的选择
- 召回不做相关性过滤：你正把噪声一股脑倒进窗口
- 历史无界增长：没有实现摘要
- 没有生成预留：模型会把自己的回复截断
- 同一条信息出现在 3 个地方（system prompt、召回的文档、历史）：去重
- Context 利用率超过 60%：留给模型"思考"的空间太小了
