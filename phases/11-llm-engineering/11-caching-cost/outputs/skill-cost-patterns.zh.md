# LLM 成本优化模式

在构建需要控制成本的 LLM 应用时，套用这套决策框架。

## 何时优化

**在以下情况立即优化：**
- 每月 LLM 支出超过 $500，或超过基础设施预算的 10%
- 面向消费者的产品，单次 query 成本高于 $0.01
- system prompt 超过 1,000 token 且随每个请求发送
- 超过 30% 的 query 是重复或近似重复的
- 你正从每天 100 用户扩展到 10,000+ 用户

**在以下情况暂时不要优化：**
- 日活不到 100，还在验证产品市场契合度
- 每月支出低于 $100 且增长缓慢
- 你还在反复调整 prompt 设计（缓存会把你锁死在某个 prompt 上）

## 缓存策略选择

### 精确缓存

**使用条件：** temperature=0、完全相同的 prompt 会重复出现、需要确定性输出。

```python
key = sha256(json.dumps({"model": m, "messages": msgs, "temp": 0}))
```

- 实现耗时：30 分钟
- 命中率：大多数应用 10-25%，FAQ bot 40-60%
- 延迟：<1ms（字典查找）
- 风险：底层数据变化时返回过期响应

**跳过条件：** temperature > 0、每次 query 都不同、需要实时数据。

### 语义缓存

**使用条件：** 用户会用不同的说法问同一个问题、FAQ 密集的产品、客户支持。

- 实现耗时：2-4 小时（embedding + 相似度 + 存储）
- 命中率：在精确缓存之上再增加 15-35%
- 延迟：10-50ms（embedding + ANN 检索）
- 风险：误命中（对相似但不同的问题返回了错误的缓存答案）

**阈值建议：**
- 0.98+：非常保守，几乎不会误命中，命中率较低
- 0.95：对事实性问答的良好平衡点
- 0.90：激进，命中率更高但存在答错的风险
- 0.85：仅用于低风险应用（建议、自动补全）

**跳过条件：** 每次 query 都有独特上下文（代码生成）、响应必须反映最新数据、query 空间无界。

### Provider prompt caching

**使用条件：** system prompt > 1,024 token（OpenAI）或该模型规定的最小长度、同一前缀会被反复发送。

| Provider | 操作 | 节省 |
|----------|--------|---------|
| Anthropic | 在 system 消息上加 `cache_control: {"type": "ephemeral"}` | 缓存前缀部分省 90%（需先付 25% 的写入溢价） |
| OpenAI | 无需操作（自动） | 缓存前缀部分省 50% |
| Google | 使用 Context Caching API 并显式设置 TTL | 缓存上下文省约 75% |

**跳过条件：** system prompt 每个请求都变、prompt 低于最小长度。

## 模型路由规则

### 基于关键词（简单、快速）

```
simple:  <= 5 words OR matches FAQ keywords -> gpt-4o-mini ($0.15/$0.60)
medium:  general queries, summaries        -> claude-sonnet ($3/$15)
complex: "analyze", "compare", "debug"     -> gpt-4o ($2.50/$10)
```

- 实现耗时：1 小时
- 准确率：70-80%
- 节省：模型成本的 40-60%

### 基于 embedding（更准确）

为每个类别标注 50-100 个 query 并做 embedding。用最近邻对新 query 分类。

- 实现耗时：4-8 小时
- 准确率：85-92%
- 节省：模型成本的 50-70%
- 额外成本：用于分类 embedding 的约 $0.02/1M token（可忽略）

### 基于 ML（生产级）

用历史 query/模型配对训练一个小分类器（逻辑回归或小型 BERT）。

- 实现耗时：1-2 周
- 准确率：90-95%
- 节省：模型成本的 60-75%
- 前提：来自生产流量的标注训练数据

## 限流配置

### 各档位的 token bucket 参数

| 档位 | Bucket 大小 | 补充速率 | 最大 RPM | 每日上限 |
|------|-------------|-------------|---------|-----------|
| Free | 50K token | 500/秒 | 10 | 50K |
| Pro | 500K token | 5K/秒 | 60 | 500K |
| Enterprise | 5M token | 50K/秒 | 300 | 5M |

### 实现清单

1. 把 bucket 存在 Redis 里（不要放在内存），以支持多实例应用
2. 使用原子操作（MULTI/EXEC）防止竞态条件
3. 拒绝响应中带上 `Retry-After` header
4. 把被拒绝的请求作为指标跟踪（>5% 被拒 = 档位限额定得太紧）
5. 实现优雅降级：先拒绝昂贵模型的请求，保留廉价模型的访问

## 预算控制

### 三阈值熔断器

| 阈值 | 动作 | 可恢复 |
|-----------|--------|------------|
| 月度预算的 70% | 记录警告，通过 Slack/PagerDuty 通知团队 | 是（自动） |
| 月度预算的 85% | 把所有流量路由到最便宜的模型 | 是（自动，下个计费周期） |
| 月度预算的 95% | 只提供缓存响应，拒绝新的 LLM 调用 | 是（手动重置或下个周期） |

### 按用户成本追踪

跟踪每个用户的累计成本。标记超出中位数 10 倍的用户。常见原因：
- 合法的重度用户（升级其档位）
- prompt injection 循环（bot 在发送自动化请求）
- 集成方式低效（客户端每次出错都重试）

### 看板上要展示的关键指标

- **单次 query 成本**（P50、P95、P99）—— 按模型、按功能、按用户档位
- **缓存命中率** —— 精确缓存 vs 语义缓存，随时间的趋势
- **模型分布** —— 各模型流量占比、各模型成本
- **预算消耗速率** —— 当前支出 vs 按当前速率推算的月度支出
- **拒绝率** —— 被限流的请求占比，按档位划分

## 常见错误

| 错误 | 为什么有害 | 修复 |
|---------|-------------|-----|
| 在 temperature > 0 时做缓存 | 输出不确定，过期的缓存会给出错误的多样性 | 只缓存 temp=0 的调用，或接受缓存响应失去随机性 |
| 语义缓存阈值太低 | 对表面相似但实际不同的 query 返回错误答案 | 从 0.95 起步，测过误命中率之后再降低 |
| 没有缓存失效机制 | 底层数据变化后响应会变旧 | 设置 TTL（动态数据 1 小时，静态数据 24 小时），数据更新时主动失效 |
| 把全部流量路由到最便宜的模型 | 质量下降，用户能感觉到 | 按复杂度路由，按档位测质量，设置质量下限 |
| 没有按用户限额 | 一个滥用用户就能烧掉整个预算 | 始终实现按用户配额，即使给得很宽松 |
| 忽视输出 token | 每个 token 的输出成本是输入的 2-5 倍 | 合理设置 max_tokens，使用 stop sequence，压缩输出 |
| 在 prompt 稳定之前就开缓存 | 缓存里堆满旧 prompt 的响应 | prompt 定稿后才启用缓存，prompt 变更时清空缓存 |
