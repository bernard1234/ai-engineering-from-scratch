给定一个由 N 个 agent 回答同一问题的集成，设计一个对三种经典 LLM agent 攻击都稳健的 consensus 协议：byzantine 谎言、谄媚式从众、相关错误单一栽培。

产出：

1. **聚类策略。** 答案如何分组？字符串规范化（小写 + 去标点）、带阈值的 embedding 相似度，还是显式结构化规范化（JSON schema）。说明预期的簇粒度错误率。
2. **加权策略。** 相对多数（计数）、confidence-probe 加权（CP-WBFT）、质量加信任（WBFT），还是基于分数并具备几何中位数稳健性（DecentLLMs）。从攻击画像出发论证该选择。
3. **阈值。** 总权重的多大比例触发接受？低于阈值时怎么办：重试、升级，还是弃权？
4. **多样性要求。** 该集成需要多少个底座模型、prompt 族或 temperature 设置？单一栽培是相对多数无法恢复的攻击；多样性是结构性的缓解。
5. **独立 verifier。** 是否存在一个只读 agent，负责获取 ground truth（当可用时）或应用评分量表？verifier 的输出去了哪里？它绝不能重新进入投票池。
6. **轮数限制。** 升级前的最大轮数。多数任务默认 2-3 轮。更长的轮数会放大谄媚。
7. **攻击测试表。** 对（byzantine、谄媚、单一栽培）中的每一种，展示预期的协议行为与残余风险。若协议存在已知的失败模式，用一句话说明。

硬性拒绝：

- 任何只在单一底座模型上做相对多数的设计。单一栽培会让它悄无声息地失败。
- 任何轮数无界或"一直辩论到达成一致"的设计。这会奖励从众。
- 任何让 verifier 的输出回流到投票池的设计。那会污染 verifier。
- 声称 BFT"解决"了分歧的说法。BFT 对齐输出；正确性是另一个问题。

拒绝规则：

- 若任务没有 ground truth（意见、综合、创意），说明这一点，并建议"consensus 作为建议，人类作为决策者"。
- 若可用的 agent 少于 3 个，consensus 不适用；改为建议单 agent 加 verifier。
- 若所有 agent 共享一个底座模型且用户无法改变，明确标记单一栽培的天花板。

输出：一份一页的设计简报。以一句话总结开头（"对 5 个 agent（3 个底座模型）做置信度加权投票，语义簇阈值 0.55，独立 verifier 重新获取来源，最多 2 轮。"），然后是上述七个部分。以攻击测试表结束。
