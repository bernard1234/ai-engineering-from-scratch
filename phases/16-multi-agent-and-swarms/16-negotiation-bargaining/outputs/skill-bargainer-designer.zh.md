给定一个谈判或任务市场场景（两方 bargain、N 方拍卖、contract-net 任务分配），设计协议。

产出：

1. **机制。** 两方 bargain、N-bidder 拍卖、contract-net 广播，还是多方联盟。说出博弈的名称。
2. **报价生成器。** 确定性（Zeuthen 式让步、Rubinstein 均衡、简单线性日程）还是 LLM prompt 生成。默认：确定性，除非报价必须是定性结构（提案、角色分配）。
3. **叙述层。** LLM 贡献什么：人类友好的包装、说服战术、人格。明确说明 LLM 不决定什么。
4. **私有与公开通道。** 推理轨迹如何被挡在对手的 context 之外。把"私有 scratchpad"与"公开消息"作为两个字段。按 arXiv:2503.06416，这点不容妥协。
5. **轮数上限。** 两方最多 3-5 轮。无界不是一个选项；它奖励从众并鼓励情绪化报价。
6. **保留价与 BATNA 纪律。** 双方都必须知道自己的保留价。若对方试探，LLM 叙述者绝不能透露它。对照这条规则校验每条出站消息。
7. **成交率监控。** 该协议的预期基线成交率（引用谈判基准中的数字：依 LLM 角色在 27%-89% 区间）。回归的告警阈值。
8. **升级。** 低于阈值的轮次、违反 ZOPA 或对手侧违规，都转交调解者 agent 或人类。

硬性拒绝：

- 任何让 LLM 在没有确定性兜底的情况下计算数值报价的设计。arXiv:2402.15813 显示这会产生约 27% 的成交率。
- 任何没有分离私有与公开通道的设计。对手会读到你的推理。
- 任何轮数无界的设计。这保证了从众驱动结果。
- 让单个 agent 同时持有买方与卖方状态的设计（角色扮演式 bargain）。私有信息属性正是该机制；合并角色会消除它。

拒绝规则：

- 若任务没有数值收益（定性谈判、合同条款），OG-Narrator 分解可能不适用。改为建议结构化提案 + schema 校验。
- 若用户无法实现独立的 scratchpad（单次 LLM 调用架构），明确标记泄露风险并建议两次调用架构。
- 若谈判是对抗性的且某方可能撒谎，建议使用调解者 agent，并记录报价以供审计。

输出：一份一页的简报。以一句话总结开头（"两方 bargain：Zeuthen 报价生成器 + LLM 叙述者，5 轮上限，独立 scratchpad，成交率低于 85% 时告警。"），然后是上述八个部分。以一条示例消息结束：对手看到什么 vs 私有 scratchpad 持有什么。
