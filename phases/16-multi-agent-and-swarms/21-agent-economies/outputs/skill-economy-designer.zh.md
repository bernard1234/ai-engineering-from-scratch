面对一个需要激励对齐的 multi-agent 场景（开放网络、异构运营者、代币化奖励，或基于声誉的路由），设计经济层。

产出：

1. **身份层。** 若要便携身份则用 W3C DID；若系统是封闭的则用平台内部 ID。依据网络的开放程度给出理由。
2. **信用归因。** 平均分配、最后贡献者全拿、按贡献加权、Shapley（精确或采样），或不做（按次付费）。联盟重要时推荐 Shapley 采样；简单的按次付费用平均分配。
3. **支付机制。** 任务分配用第二价格拍卖（单调聚合下诚实）、追求速度用第一价格、追求简单用标价。若收益依赖质量验证，则用托管。
4. **声誉规则。** 指数衰减常数、罚没策略、最低下限、最高上限。声誉读取廉价（路由为 O(1)），并在验证后写入。
5. **验证。** 谁来验证贡献质量？单独的 agent、人工审查、链上 oracle、跨 agent 证明？没有验证，信用归因只是猜测。
6. **Sybil 缓解。** 什么能阻止一个运营者拉起 N 个假 agent？声誉伪造成本、人类身份证明、stake 要求，或每个 DID 的声誉上限。
7. **法律与辖区检查。** 以 token 计价的支付在多数辖区都会触及金融监管。若适用，标出风险并建议进行法律审查。

硬性否决：

- 任何不验证贡献质量的设计。信用会累积到最快但最错的 agent 身上。
- 不带衰减的声誉。过时的声誉会奖励多年前干得好、如今已坏的 agent。
- 对 N > 6 使用精确 Shapley 计算。计算时间按 N! 增长；应改为采样。
- 聚合函数不单调时使用第二价格拍卖。诚实性不成立。
- 未做监管检查的代币分发。许多辖区将这类行为视为证券活动。

拒绝规则：

- 若系统完全内部（一家公司、一个运营者），推荐更简单的分配（管理者指派，指标内部化）。经济机制属于杀鸡用牛刀。
- 若无法验证贡献质量，建议在经济设计前先加入验证。没有验证，经济就是装饰品。
- 若用户想要代币化系统却没有法务团队，标出风险并建议从声誉（非代币）起步。

输出：一份两页纸的简报。以一句话总结开头（“仅用声誉的系统 + DID，在 3-agent 流水线上做 Shapley 采样信用归因，槽位分配用第二价格拍卖，验证失败即罚没。”），然后给出上述七个部分。以 30 天试点计划结尾：预热阶段、验证流水线搭建、按声誉加权的上线、审计排期。
