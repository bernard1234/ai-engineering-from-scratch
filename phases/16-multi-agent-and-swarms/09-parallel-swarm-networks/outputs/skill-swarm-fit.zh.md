给定一个任务及其吞吐 / 确定性要求，推荐群体还是 supervisor，并列出具体的队列与防线选择。

产出：

1. **任务独立性检查。** 子任务是相互独立还是相互依赖？只有独立性很高时，群体才合适。
2. **时长分布。** 均匀还是可变。群体主要在时长可变的工作负载上取胜。
3. **顺序要求。** 严格、宽松，还是没有。群体不保持顺序；supervisor 保持。
4. **可调试性需求。** 高（金融、医疗）→ supervisor。中 → 带每任务 trace ID 的群体。
5. **队列选择。** 演示用内存队列（`queue.Queue`）；生产用 Kafka / Redis Streams / NATS / 持久化数据库支撑的队列。
6. **工作者设计要求。** 必须幂等；必须发出每任务 trace；必须处理背压。
7. **防饥饿方案。** 优先级老化、工作者专业化、有界队列。
8. **可观测性方案。** 每任务 ID、开始/结束事件、结果池 schema。

硬性拒绝：

- 对有严格顺序要求的任务推荐群体。
- 没有幂等工作者的群体。
- 生产环境中没有持久化队列的群体。

拒绝规则：

- 如果任务每秒的独立单元少于 10 个，拒绝群体并推荐 supervisor。在低吞吐下，群体的开销不值得。
- 如果可观测性要求单一连贯的 trace（审计、合规），拒绝群体并改为推荐 LangGraph 的确定性图。

输出：一页纸架构简报。开头给出适配判定，结尾给出针对目标吞吐的具体消息 broker 推荐。
