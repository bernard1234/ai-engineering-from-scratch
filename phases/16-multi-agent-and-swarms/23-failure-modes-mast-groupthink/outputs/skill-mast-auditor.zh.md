给定一个多 agent 系统和抽样执行 trace，执行失效模式审计。

产出：

1. **样本构造。** 至少 200 条生产 trace，在任务类型与时间窗口上均匀抽样。记录抽样方法与偏差风险。
2. **分类环节。** 对每条 trace 标记 `success | failure`。对失效的，指定一个 MAST 类别（spec / coord / verify），并在适用时指定一个或多个 Groupthink 家族标签（monoculture / conformity / tom / mixed-motive / cascade）。
3. **分布表。** 按 MAST 类别与 Groupthink 标签统计计数与百分比。与 Cemri 2025 的参考分布（41.77 / 36.94 / 21.30）对比。严重偏离参考的系统往往有特定的薄弱层。
4. **高频失效模式。** 找出 3 个最频繁的具体模式（例如"两个 agent 都在评审"）。记录复现步骤。
5. **缓解排序。** 对每个高频模式，从标准库中提出一项缓解措施：显式角色契约、带版本的共享状态、独立验证器、circuit breaker、detection-diagnosis-validation（STRATUS）三件套。按该模式出现频率下的预期失效削减量排序。
6. **静默失效风险。** 有多少失效产出"看似合理但错误"的输出，而非响亮报错？静默比例决定了验证层的投入。
7. **慢失效代理指标。** 推荐 2-3 个能在漂移变成响亮错误之前暴露它的实时指标：一致率、重试率、输出长度分布、agent 间编辑距离。

硬性否决：

- 没有随机或分层抽样的审计。手工挑出的失效会过度代表戏剧性案例，漏掉慢失效漂移。
- 没有基线测量的缓解建议。不知道当前失效率时，"加个验证器"毫无意义。
- 忽略 MAST 无法归类的事件。若某 trace 不符合任何类别，说明分类法不完整；应提出扩展，而不是硬塞进某个类别。
- 声称季度审计足够，却没有运行态慢失效监控。季度审计会漏掉两次审计之间的漂移。

拒绝规则：

- 若 trace 缺少逐 agent 归因（谁写了什么、谁读了什么），审计无法区分协调失效与角色冲突。建议先补上结构化的逐 agent 日志再重审。
- 若系统累计失败 trace 少于 50 条，样本太小，无法给出分布估计。建议延长观察窗口。
- 若 trace 含 PII，先脱敏再分析。

输出：一份三页的报告。先用一句话给出总结（"41% spec 失效、12% 协调失效、39% 验证缺口、8% 未知；最高频模式是双评审冲突；ROI 最高的缓解是显式角色契约。"），然后是上面七个部分。最后给出按优先级排序的行动清单：三项缓解，附预估实现成本与预期失效率削减。
