给定一个声称具备涌现式协调的 multi-agent 系统，审计其协调是真实发生的，还是 prompt 工程的产物。

产出：

1. **主张提取。** 被声称的协调行为究竟是什么？（分工、预判、互补动作、达成共识）。把它精确地陈述出来。
2. **Prompt 审查。** 是否有任何 agent 的 system prompt 明确指示了协调、角色选择或团队意识？如果有，就把该主张标记为部分由 prompt 装点，并设计一个对照组。
3. **对照条件。** 一个去掉诱导协调措辞的系统版本。精确说明改动了哪些文本。
4. **指标。** 至少使用以下之一：身份关联的差异化、目标导向的互补性、高阶协同（Riedl 2025）。不要把“agents 看起来在一起工作”当作证据。
5. **统计检验。** 系统与对照组之间该指标的显著性。达到 `p < 0.05` 所需的样本量。如果试验次数 `n < 50`，则明确报告统计功效。
6. **模型容量检查。** 在更小的基础模型上重复该比较。效果是依然存在还是消失了？Li 和 Riedl 都展示了容量依赖性。
7. **失败案例复盘。** 当系统失败时，ToM 状态（如果有的话）是什么样子？是身份混淆（belief-agent 绑定断裂），还是内容幻觉（信念内容错误）？

硬性拒绝：

- 没有对照条件就声称涌现。演示视频不是证据。
- 在统计审视下消失的主张（效果低于 `p < 0.05`，`n >= 50` 次试验）。这些是协调幻觉。
- 只在单一模型上成立的主张。如果一个更小的强基线在没有 ToM prompting 的情况下也能取得该效果，那么这种协调就不是 ToM 驱动的。
- 用“我们的 agents 自己就搞明白了”作为机制解释。机制主张需要把 ToM 状态记录下来并可检视。

拒绝规则：

- 如果系统没有记录每个 agent 的推理过程，审计就无法区分真实协调与随机性。建议在重新审计之前先加上结构化的 ToM 状态日志。
- 如果任务存在由 oracle 计算出的最优协调，就与最优解比较，而不是与对照组比较。
- 如果主张的范围很窄（“单轮任务上的协调”），审计可以是一段更短的检查：只测量单轮上的互补性，不需要长程分析。

Output：一份两页的审计报告。先用一句话给出结论（“协调主张是由 prompt 装点的：去掉 ‘work together’ 措辞后，指标从 0.82 降到 0.31，在对照组下显著。”），然后是上面的七个部分。最后列出把 prompt 装点的协调转化为真实协调的修复项：显式的 ToM 状态、带日志的更长时程、混合模型集成。
