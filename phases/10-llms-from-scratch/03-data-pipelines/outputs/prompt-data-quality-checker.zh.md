# LLM 预训练的数据质量检查器

当你为 LLM 预训练构建或审计数据流水线时，用这个框架在问题到达模型之前把它们抓出来。

## 流水线输出中的危险信号

**Deduplication 移除的网页数据不足 20%。** Common Crawl 通常包含 30-40% 的重复内容。如果你的 dedup 步骤移除不到 20%，说明你的 MinHash 参数太保守，或者阈值太高。检查：shingle 大小 k、哈希函数数量、LSH band 数量、Jaccard 阈值。

**压缩比低于 2.0 chars/token。** 这意味着你的 tokenizer 切分得太激进。要么用更多 merges 重新训练，要么增大词表，要么检查 pre-tokenization 是否在不必要地碎片化文本。

**压缩比高于 6.0 chars/token。** 你的 tokenizer 学到了非常领域专用的 merges，可能无法泛化。这对领域专用模型没问题，但对通用模型是警告信号。

**序列利用率低于 90%。** padding 太多。要么你的文档太短（过滤掉它们或提高最小文档长度），要么你的序列打包效率低（从朴素 padding 换成多文档打包）。

**词表利用率低于 50%。** 你的词表有一半以上在这个语料上没被用到。要么词表对你的领域太大，要么 tokenizer 是在差异很大的数据上训练的。

## 质量过滤器校准

在每个流水线阶段对 1,000 篇文档的随机样本运行这些检查：

1. **清洗后随机读 20 篇文档。** 是否残留 HTML、JavaScript、导航文本或样板内容？如果是，你的 HTML 剥离不彻底。

2. **随机读 20 篇通过了质量过滤器的文档。** 是否有垃圾内容、关键词堆砌或机器生成内容？如果是，收紧过滤阈值。

3. **随机读 20 篇未通过质量过滤器的文档。** 是否有真正优质的内容？如果是，你的过滤器过于激进。放宽阈值，或为特定模式添加例外。

4. **随机读 20 对 dedup 的近重复文档。** 它们真的相似吗？如果不相似，降低 Jaccard 阈值或增加哈希函数数量。

## 数据配比

没有通用公式。从这些基线开始，再根据评估调整：

| 类别 | Llama 3 比例 | 起始值 |
|----------|--------------|----------------|
| 网页文本 | 50% | 50% |
| 代码 | 25% | 15-25% |
| 书籍/学术 | 13% | 10-15% |
| 数学 | 8% | 5-10% |
| 多语言网页 | 4% | 5-10% |

如果模型需要擅长编程，就提高代码比例。如果推理很重要，就提高数学比例。如果需要更少噪声，就降低网页比例。调整比例后一定要在 benchmark 上评估。

## 规模估算

对于给定目标 token 数：

- 1T tokens 来自网页：预计约 3-5TB 原始文本，清洗与 dedup 后约 1.5-2TB
- Tokenization 速度（Rust）：每核约 100M tokens/second
- Tokenization 速度（Python）：每核约 1-10M tokens/second
- MinHash dedup，128 个哈希、16 个 band：每核约 10K 文档/second
- 序列打包：I/O 受限，语料超过 10GB 时使用 memory-mapped 文件

对于 15T tokens（Llama 3 规模），规划约 30-50TB 原始输入数据、在 64 核机器上 1-2 周的预处理时间，以及 100TB+ 的中间文件磁盘空间。

## 训练前检查清单

1. 总 token 数符合你的算力预算（以 Chinchilla scaling 或 Llama 3 的 overtrain 比例为指导）
2. Dedup 移除了 30-40% 的网页数据
3. 质量过滤器移除了剩余数据的 10-20%
4. 英文的压缩比在 3-5 chars/token
5. 序列利用率高于 95%
6. 随机抽查显示每个流水线阶段的文本都干净、连贯
7. 数据配比已通过小规模训练验证
8. PII 移除已在样本上验证
9. 所有二进制格式（打包序列、token ID 数组）通过往返编解码测试
10. 流水线可复现：固定随机种子下，相同输入产生完全相同的输出
